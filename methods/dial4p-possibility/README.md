## Definition

DIAL-4P Possibility is the composed framework in which:

1. **DIAL-4** classifies the claim as Deduction, Inference, Abatement or Legitimation.
2. **DIAL-4+** grades the claim by confidence, evidence quality and scope.
3. **Diátaxis** assigns the appropriate documentation form: tutorial, how-to guide, reference or explanation.
4. **5PP possibility governance** controls what happens to unresolved claims through Clarification, Scope Validation, Reasoning Plan, Execution and Verification.

The `P` in this profile means **Possibility**.

It is not ChangePlane's separate DIAL-4P meaning, where `P` means Projection/Productization and an existing trace is rendered into a derived artifact.

## Governing rule

> Preserve possibility space unless evidence, explicit constraints, contradiction, internal incoherence, impossible premises or a hard non-negotiable limitation force collapse.

Possibility preservation is not permission to overclaim. The framework requires classification, scope, falsifiers, operational division, proof paths and verification.

## Status taxonomy

The full operating prompt names nine statuses:

1. Confirmed
2. Plausible
3. Emerging
4. Could Be
5. Not Yet Evidenced
6. Blocked by Current Tooling
7. Buildable with Custom Engineering
8. Impossible Under Current Constraints
9. Out of Scope

The public article uses a compact six-status subset:

- confirmed
- plausible
- emerging
- buildable with custom engineering
- blocked by current tooling
- not yet evidenced

The profile preserves this as a source-surface difference. It does not silently normalize the article and prompt into one supposedly canonical list.

## Anti-collapse rules

A possibility must not be rejected merely because it:

- is not a finished product;
- lacks packaging;
- is not standardized;
- has no dominant implementation;
- requires engineering effort;
- is only partially evidenced.

Rejection becomes justified only when the possibility:

- contradicts explicit constraints;
- violates core logic;
- is internally incoherent;
- depends on impossible premises;
- is blocked by a stated hard non-negotiable limitation.

`Out of Scope` is not the same as invalid. It is a routing decision.

## Operational division

The method requires unresolved possibilities to be split into implementation-relevant units such as:

- modules;
- tracks;
- subsystems;
- interfaces;
- dependencies;
- workflows;
- risks;
- proof paths;
- implementation layers;
- atomic work units that can progress independently.

A generic layer model in the source records includes source, transformation, rendering or delivery, automation, validation, governance, and deployment or execution.

## Source-contract boundary

The long master prompt first requires ten output sections:

1. Task Restatement
2. Scope Boundaries
3. Memory and Capability Check
4. Possibility Map
5. Operational Divisions
6. What Exists / What Could Be / What Is Blocked
7. Implementation Pathways
8. Risks, Dependencies, and Unknowns
9. Verification Against 5PP
10. Final Structured Verdict

The subsequent `Output Schema` contains nine sections and replaces parts of that structure with `What Must Not Be Collapsed Prematurely`.

This profile presents both forms and does not invent an unrecorded reconciliation.

## Non-claims

The profile does not claim that:

- every unresolved idea should be preserved indefinitely;
- lack of evidence is evidence of feasibility;
- classification makes a claim true;
- operational division guarantees implementation success;
- required memory and tool use are mechanically enforced by the prompt text;
- 5PP compliance has been independently measured here;
- Diátaxis is part of the original DIAL-4 framework outside this composed first-party model;
- ChangePlane Projection/Productization is the same framework as DIAL-4P Possibility;
- a deterministic DIAL-4P Possibility validator has been delivered.
