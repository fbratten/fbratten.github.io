<section class="lab-panel" aria-labelledby="overview-title">
 <h2 id="overview-title">1. What is actually happening in GitHub?</h2>
 <p>A <strong>workflow</strong> is a reusable recipe stored as a YAML file in <code>.github/workflows/</code>. A <strong>workflow run</strong> is one execution of that recipe. The run can contain several <strong>jobs</strong>, and every job consists of <strong>steps</strong> executed by a <strong>runner</strong>.</p>
 <div class="actions-pipeline" aria-label="Workflow hierarchy">
  <div><span>01 / Code</span><strong>Commit + push</strong><small>Save a version of the website and notify GitHub</small></div>
  <div><span>02 / Workflow</span><strong>pages-browser-check.yml</strong><small>The reusable YAML recipe</small></div>
  <div><span>03 / Run</span><strong>Run ID</strong><small>One recorded attempt for one commit and event</small></div>
  <div><span>04 / Job</span><strong>verify</strong><small>A runner executes a collection of steps</small></div>
  <div><span>05 / Evidence</span><strong>Tests + receipts</strong><small>Browser checks, screenshots and status</small></div>
 </div>
 <p class="lab-note">The word <strong>step</strong> is not interchangeable with <strong>job</strong>. Your example ID <code>117505847884</code> identifies one job, not the workflow definition. The enclosing run is <code>39070132534</code>.</p>
</section>

<section class="lab-panel" aria-labelledby="condition-title">
 <h2 id="condition-title">4. Experiment: change the run trigger</h2>
 <p>The same workflow can behave differently when started by a <strong>push</strong>, a <strong>pull request</strong> or <strong>workflow_dispatch</strong> (explicit start). Change the event and predict which conditional steps would be eligible to run.</p>
 <div class="lab-tagline"><strong>Simulation, not another GitHub run.</strong> This exercise interprets explicit workflow <code>if:</code> conditions. It does not predict whether eligible steps would pass, whether deployment would succeed or whether earlier failures would cancel later work.</div>
 <div class="actions-toolbar">
  <label for="trigger-select">Choose trigger</label>
  <select id="trigger-select"><option value="push">push to main</option><option value="pull_request">pull_request</option><option value="workflow_dispatch">workflow_dispatch</option></select>
 </div>
 <div id="condition-summary" class="lab-note" aria-live="polite"></div>
 <div id="condition-list" class="actions-conditions" aria-label="Predicted event-gated steps"></div>
 <p class="lab-small lab-muted">The condition <code>if: always()</code> allows screenshot-upload steps to run after a failure. <code>if: failure()</code> enables diagnostics only after failure. The exercise marks that dependency rather than inventing a result.</p>

<section class="lab-panel" aria-labelledby="bug-title">
 <h2 id="bug-title">5. Debug a real failed job</h2>
 <p>During the first Mutation Gate lab rollout, Playwright opened a 390-pixel mobile viewport and found the page was 456 pixels wide. That violates the test's assertion, so the job correctly failed. No GitHub deployment was proven by that run.</p>
 <div class="actions-debug">
  <div class="actions-debug-screen" aria-label="Illustration of viewport overflow">
   <span>390 px phone viewport</span><div class="actions-viewport"><div class="actions-overflow">456 px page content</div></div>
  </div>
  <div class="actions-debug-copy">
   <h3>Actual test failure, 17 October 2026</h3>
   <pre>AssertionError: Mobile overflow on
/labs/mutation-gate/
{"width":456,"viewport":390}</pre>
   <p><strong>Root symptom:</strong> the page required sideways scrolling on a phone. The subsequent repair made long technical identifiers wrap, followed by another CI run on the corrected code.</p>
   <p><a href="https://github.com/fbratten/fbratten.github.io/actions/runs/39068541958" target="_blank" rel="noopener">Inspect the original failed run</a></p>
  </div>
 </div>
 <p class="lab-lesson">A failed assertion is useful evidence, not a reason to hide the job or mark it green. The developer changes the code, pushes a new commit and runs the checks again.</p>
</section>
<section class="lab-panel" aria-labelledby="deploy-title">
 <h2 id="deploy-title">6. A green job is not the entire delivery story</h2>
 <p>For the approved merge commit, a separate GitHub Pages build/deployment run also completed successfully. The <code>verify</code> job then exercised the public website. These are distinct outcomes:</p>
 <div class="lab-grid-3">
  <div class="lab-datum"><h3>CI checks</h3><p>Local static and browser tests check the downloaded code. Green tests prove only their declared scope.</p><p><a href="https://github.com/fbratten/fbratten.github.io/actions/runs/39070132534" target="_blank" rel="noopener">Successful verification run</a></p></div>
  <div class="lab-datum"><h3>Deployment</h3><p>A different workflow builds and publishes the website to GitHub Pages. It has its own run ID and outcome.</p><p><a href="https://github.com/fbratten/fbratten.github.io/actions/runs/39070132389" target="_blank" rel="noopener">Pages deployment run</a></p></div>
  <div class="lab-datum"><h3>Live acceptance</h3><p>The verification workflow opens the public Pages URL and repeats the browser checks. A checked deployment is not the same as permanent uptime.</p><p><a href="https://fbratten.github.io/labs/mutation-gate/">Visit the published Mutation Gate lab</a></p></div>
 </div>
 <p class="actions-boundary"><strong>Evidence boundary:</strong> the run IDs and results are historical snapshots. This lab does not claim that a new deployment is happening now. An uploaded artifact is not a test verdict; a successful build is not proof that every feature is correct.</p>
</section>
