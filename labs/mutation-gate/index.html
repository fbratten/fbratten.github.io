Mutation Gate Lab

What if your tests are green only because the code path was never exercised? Break a protection on purpose and find out whether the tests notice.

Learn software engineering by doing. The interactive experiments below are browser-local simulations. They do not run Python, mutate repositories, call GitHub, or inspect live services. Separately, the dated CI evidence refers to a real October 2026 run.
1. Testing architecture 2. Fault injection & test gates 3. AI evaluation & CI/CD 4. Mutation Gate 5. GitHub Actions

1. From a Git commit to a CI result

A repository holds source files and their Git history. A developer works in a branch or separate worktree, saves changes in a commit and pushes that branch to GitHub. GitHub Actions reads a workflow file (.github/workflows/tests.yml) and starts isolated runners to execute the configured jobs. A successful push is not a merge to main, and a green pipeline is not the same as independent approval.

Step 01Change

Edit and test in a separate branch and worktree.

Step 02Commit + push

Record a particular version and publish it to a review branch.

Step 03CI jobs

GitHub's runners execute tests in new, controlled environments.

Step 04Review + PR

Interpret what passed, what was skipped, and what still needs human or independent review.

The full commit hash (SHA) identifies exactly which code was tested. The workflow is configured in version control; it is not an invisible or magical action by an AI model.

3. Why Mutation Gate exists

A normal assertion asks whether a feature produces the expected result. Mutation testing asks the harder question: would that assertion fail if we deliberately removed the protection that supposedly caused the result?

In this project's earlier testing, a path-traversal protection was deliberately removed, yet its test stayed green because a separate file-extension check blocked the test payload first. The test was not observing the protection it claimed to verify. That is a false-green test, not evidence that the removed guard worked.

BaselineControl present

The named test must run and pass against the original code.

MutationSabotage a copy

A tiny targeted change disables one named protection in an isolated scratch copy.

DetectionTest goes red

A real assertion must fail in the test body for the intended property.

GateInterpret result

CAUGHT is good; ESCAPED is a test gap; BROKEN is inconclusive.

CAUGHT

Baseline passes; the intentionally damaged version fails its own assertion. The test can detect this specific fault.

ESCAPED

The damaged version stays green. The test missed the control, or another guard masked the problem.

BROKEN

Setup, anchoring or execution failed. It would be dishonest to count the result as a detected bug.

Before any mutation is scored, the harness checks that its scratch copy is actually used, that the source anchor matches exactly once, and that the edit genuinely changed the code. A setup ERROR or skipped test cannot masquerade as a CAUGHT assertion failure.

5. What the second review actually uncovered

 
Eleven serious findings across three adversarial lenses led to the Option-A repair and the 13 new mutations above. Some findings are different descriptions of the same root cause. They are not the same thing as 11 mutation tests.

 

  
Findings 2, 5 and 7: group ID values
The group key was validated but the internal group.id value was used in rendered handlers without equivalent validation. A new rule checks both values and their agreement.

  
Finding 3: group node lists
A collapsed group could display malformed group.nodes data as HTML. The input validator now requires a proper array of node IDs.

  
Findings 4 and 8: rollback was unreachable
Rendering happened before the try/catch. If drawing failed, the old graph was not restored. The repair moves risky rendering inside the recovery boundary.

  
Finding 6: lost unsaved edits
A pushed update closed the inspector and discarded what the user was still typing. The repair preserves the inspector when its node is unchanged.

  
Finding 9: shadowed test
A malformed ID test failed for a different reason than intended. The revised case isolates its ID-shape rule and requires a specific refusal reason.

  
Finding 10: incorrect test isolation claim
Additional file:// browser tests had the live bridge active. The harness now disconnects file-based tests and the changelog was corrected.

  
Findings 1 and 11: unresolved HTML sinks
Some node and edge text can still reach unsafe HTML insertion paths. This broader escaping sweep remains separate work, so live state mirroring is OFF by default.

  
Two kinds of evidence
Mutation Gate confirms a selected test detects selected sabotage. An independent code review searches for unknown paths, false assumptions and missing controls. Both are needed.

 






 
6. Quick challenge: when can you trust the result?

 
Your test passes. You remove the guard it claims to check. What would be the strongest evidence that the test really exercises that guard?
 
 
 
 
Choose an option and check your reasoning.

 
A non-vacuous test also proves a positive case works. For example, after rejecting malformed WebSocket messages it must still accept a valid message through the same connection. Five selected new tests were additionally shown to fail for the intended reasons against the earlier, unrepaired canvas.






 
7. What green CI cannot certify

 
The real mutation run recorded 73 CAUGHT, 0 ESCAPED, 0 BROKEN. That supports the named safety controls, not every possible input, interaction or security risk. In particular, the approximately 53 still-unsafe HTML insertion sites were not all removed by Option A, and enabling live mirroring remained a user opt-in with a warning.

 
The third independent security review is tracked separately. This lab freezes a dated learning example; its review status must not be mistaken for current deployment state. Passing CI, passing independent review, merging a PR and releasing a product are four different claims, each needing its own evidence.
